# 개발 회고: 급등주 초단기 예측 프로젝트

2026년 9월 – 11월 · Kiwoom Intraday Signal Research

이 프로젝트는 급등하는 주식의 추가 상승을 구분해 볼 수 있지 않을까 하는 호기심에서 시작했습니다. 처음에는 자동매매를 구현하는 데 관심이 컸지만, 데이터가 쌓이고 실험이 반복될수록 질문이 달라졌습니다.

> 가격이 오를 때를 어느 정도 구분하더라도, 거래비용과 손절 위험을 감수한 뒤 실제로 남는 수익이 있을까?

결론적으로 이 질문에 긍정적인 답을 얻지 못했습니다. 대신 약 두 달 동안 실시간 데이터 수집 환경, 머신러닝 학습 파이프라인, 다양한 검증 방법을 만들고 운영하며 어떤 부분이 어려웠는지 기록으로 남겼습니다.

## 1. 시작할 때의 생각

초기의 가설은 세 단계였습니다.

1. 급등주는 짧은 시간에 큰 가격 변동을 만든다.
2. 그중 일부는 상승 흐름을 이어간다.
3. 추가 상승 가능성이 높은 신호를 구분할 수 있다면 초단기 거래에 활용할 수 있다.

처음에는 거래당 약 1%의 수익을 목표로 하는 접근을 검토했습니다. 목표는 나중에 0.40–0.50% 수준으로 낮추고, 30초·60초·120초처럼 짧은 보유시간을 비교하는 쪽으로 수정했습니다. 장기 목표였던 월 2% 순수익 역시 어디까지나 개발 목표였지 달성한 성과는 아닙니다.

계획한 개발 단계는 `COLLECT → Shadow → MOCK → LIVE`였습니다. 실제로 진행한 단계는 데이터 수집과 오프라인 분석까지였고, **실제 주문은 실행하지 않았습니다.**

개발이 진행되면서 '급등주는 변동성이 크다'는 사실만으로 '추가 상승을 예측할 수 있다'거나 '수익을 낼 수 있다'는 결론이 나오지는 않는다는 점을 점차 분명하게 인식했습니다.

## 2. 개발 과정

### W37 — 실시간 수집 환경 구축

9월 초에는 키움증권 API를 이용한 실시간 시세·호가·체결 데이터 수집과 신호 생성, SQLite 저장, 주간 데이터 관리 기능을 구성했습니다. 기존 기록상 첫 공식 수집은 2026년 9월 11일입니다.

초기에는 수집, 신호 생성, 모델 평가, 자동매매까지 하나의 흐름으로 연결하는 구상이 있었습니다. 하지만 당시 작성된 설계와 실제 동작이 확인된 기능은 구별할 필요가 있습니다. 최초 개발 대화가 모두 남아 있지는 않아 세부 구현 순서도 완전히 복원할 수는 없습니다.

### W38 — 서버 한계와 역할 분리

수집 데이터가 늘면서 2 vCPU, 8GB 메모리의 Linux 서버에서 메모리 부족과 디스크 포화 문제가 발생했습니다. 데이터셋 생성과 학습, 백업이 한꺼번에 돌아가는 구조를 유지하기 어려웠습니다.

이때 서버 사양만 늘리기보다 역할을 나누는 방향으로 전환했습니다.

- 서버: 실시간 수집, 전처리, 압축, 주간 데이터 관리
- Google Drive: 데이터 전달 및 보관
- Google Colab: 모델 학습과 오프라인 분석

운영 문제를 해결하는 과정에서 데이터 처리를 청크 단위로 나누고, 샘플링을 적용하고, 스키마·타임스탬프·피처 누락 문제를 점검했습니다. 전략 검증 이전에 안정적으로 데이터를 쌓고 다시 읽을 수 있는 구조가 필요하다는 것을 경험한 시기였습니다.

### W39 — 어떤 구간에서 신호가 의미가 있는가

이 시기에는 단순히 모델 점수가 높은 신호만 모아 보는 방식에 의문을 가졌습니다. 상위 점수 누적 구간의 평균이 좋아 보여도, 실제로 어느 구간에서 차이가 발생했는지 드러나지 않을 수 있기 때문입니다.

그래서 점수 구간을 나누고, 시간대와 보유시간을 조합해 비교하는 방식으로 분석을 넓혔습니다. 오전장에 집중할지, 익절 목표를 낮출지, 보유시간을 줄일지 등의 선택지를 검토했습니다.

일부 실험에서 비용 차감 전 성적이 상대적으로 나은 구간도 있었지만, 이를 곧바로 일반화 가능한 모델의 우위로 판단하지는 않았습니다. 결과가 데이터 분할, 점수 출처, 필터 적용 여부에 민감할 수 있었기 때문입니다.

### W40 — 저장과 백업도 개발의 일부

원본 데이터가 누적되면서 디스크 사용량이 반복적으로 늘었고, 주말 백업 및 정리 방식도 여러 번 손봐야 했습니다. 데이터를 충분히 남겨 후속 분석에 활용하려는 목표와 한정된 서버 용량 사이에서 균형을 잡는 일이 필요했습니다.

거래를 오전에만 고려하더라도 오후 데이터까지 수집해야 실패 사례와 시간대별 차이를 확인할 수 있다는 판단으로 종일 수집 방향을 유지했습니다.

W40에 운영 관련 기록은 있지만, 최종 누적 학습 데이터셋에 W40 샘플은 포함되지 않았습니다.

### W41 — 미래 가격보다 가격 경로가 중요했다

처음에는 진입 후 30초나 60초의 수익률을 주로 살펴봤습니다. 하지만 미래 시점의 가격이 높았다는 사실만으로 그 전에 손절하지 않고 버틸 수 있었는지는 알 수 없습니다.

이 문제를 검토하면서 목표가와 손절가 중 어느 쪽에 먼저 도달하는지 보는 `Target-First / Stop-First` 분석을 시도했습니다. 가격의 마지막 상태만 보던 평가에서 실제 거래 가정에 더 가까운 질문으로 옮겨간 셈입니다.

그 과정에서 학습·분석·운영 코드 사이의 불일치도 점검했습니다. 입력 피처가 23개, 24개, 25개 버전으로 달라지는 문제, `ret_60s_pct` 라벨 처리, 학습 가중치를 서버 추론 경로에 연결하는 방식 등이 대표적입니다.

손절에 먼저 도달한 사례에 더 큰 페널티를 주는 손실 함수 개선도 검토했지만, 그것으로 수익성이 확보됐다고 볼 재학습·검증 결과는 확인되지 않았습니다.

### W42 — 평가하는 점수부터 다시 확인했다

이 시기에는 시장을 잘 예측했는지 이전에, **실제로 어떤 신호를 평가하고 있는지**부터 점검했습니다. 신호의 승인·차단 이유, 점수의 출처, 학습 모델이 적용됐는지 여부를 확인하는 작업이었습니다.

`research_final_signal_test_v1`의 신호 정의 점검 자료에는 W41과 W42의 신호 3,257건이 들어 있습니다.

| 차단 사유 | W41 | W42 | 합계 |
| --- | ---: | ---: | ---: |
| 체결강도 부족 | 549 | 831 | 1,380 |
| 시가총액 구간 비활성화 | 662 | 660 | 1,322 |
| 학습 모델 요구 조건 미충족 | 221 | 286 | 507 |
| 단기 틱 수 부족 | 30 | 8 | 38 |
| VI 근접 차단 | 6 | 4 | 10 |
| **합계** | **1,468** | **1,789** | **3,257** |

이 자료의 모든 신호는 `approved=0`, `trained_model=0`으로 기록됐고, 모델 출처는 `RUNTIME_JSON_PRETRAIN_ONLY`였습니다. 점수 중앙값은 W41 약 64.994점, W42 약 64.988점이었습니다.

이는 이 신호 집단에서 학습 모델의 실제 출력과 기본·대체 점수를 구분해야 한다는 뜻입니다. 다른 실험에 사용한 모델까지 모두 미적용이었다고 일반화할 수는 없습니다.

오프라인 성적을 읽기 전에 **입력 데이터와 점수의 의미부터 확인해야 한다**는 점을 분명히 보여준 사례였습니다.

### W43–W44 — 수익이 나지 않는 이유를 더 세분화했다

이후 Google Drive에 보존된 연구 디렉터리에는 피처 추가·제거, 모델 비교, 신호 선별, 호가와 스프레드, 주문 가능 가격과 지연, 단기 가격 변화 등을 다룬 분석 자료가 있습니다.

이 시기의 관심은 모델을 하나 더 만드는 것만이 아니라, 신호가 좋아 보여도 실제로 수익이 남지 않는 이유를 나누어 살펴보는 데 있었습니다.

다만 현재 확인한 자료 중 일부는 폴더 목록만 확보된 상태입니다. 따라서 특정 피처의 개선 효과나 모델 간 우열을 모두 검증된 결론처럼 정리하지는 않았습니다.

### W45–W46 — 데이터 수집은 이어졌지만 개발은 종료했다

W45에는 한 주차 파이프라인에서 원본 신호 약 299만 건, 미래 진단 생성 약 269만 건이 처리됐다는 로그가 남아 있습니다. 이 수치들은 정제된 모델 학습 샘플과 다른 집계입니다.

11월 9일에는 프로젝트를 더 확장하지 않기로 결정했습니다. 이후에도 W46 데이터 수집과 주간 처리·백업 정리는 이어졌으며, 소스코드와 모델, 실험 자료, 운영 기록을 Google Drive에 보존하는 작업을 진행했습니다.

W46 기준 누적 학습 데이터 매니페스트에는 W37–W39, W41–W46의 36거래일, 1,366종목, 정제 샘플 1,255,662건이 기록돼 있습니다. W40은 이 집계에서 제외됩니다.

## 3. 실험을 통해 바뀐 생각

### 상승 가능성과 기대 수익은 다르다

급등한 종목에 추가 상승이 나타나는 경우가 있어도, 그 자체로 수익성 있는 진입 신호라는 의미는 아닙니다. 변동성이 크면 상승뿐 아니라 역행과 손절 위험도 커질 수 있습니다.

처음에는 '어떤 신호가 더 잘 오르는가'를 중심으로 생각했다면, 후반에는 '가격 경로와 거래비용을 반영해도 우위가 남는가'를 더 중요하게 봤습니다.

### 거래비용을 넣으면 평가가 달라진다

많은 실험에서 왕복 거래에 따른 마찰 비용을 약 0.25%로 가정했습니다. 이 수치는 실거래 체결 내역에서 산출한 값이 아니라 분석용 가정입니다.

예를 들어 60초 보유 가정의 `AFTER_10 / C2` 집단은 W41에서 522건의 평균 -0.2022%, W42에서 821건의 평균 -0.2155%로 기록됐습니다. 특정 집단의 오프라인 출력일 뿐 프로젝트 전체의 손익을 나타내지는 않습니다.

다른 초기 Colab 분석에서는 점수 컬럼이 없을 때 기본 점수로 대체하는 로직 때문에, 의도한 상위 점수 필터가 적용되지 않았을 가능성도 확인됐습니다. 숫자를 얻는 것만큼 **그 숫자가 어떤 조건에서 계산됐는지 확인하는 일**이 중요했습니다.

### 수집 시스템이 돌아간다는 것과 전략이 유효하다는 것은 다르다

실시간 수집과 주간 데이터 생성은 일정 기간 지속할 수 있었지만, 그것이 모델의 예측력이나 거래 전략의 수익성을 보장하지는 않았습니다. 실제 체결까지 고려한 운영 성적도 확보하지 못했습니다.

개발 과정에서 오류를 고치고 파이프라인을 자동화한 성과와, 투자 전략의 효과를 입증했는지는 분리해 평가하는 것이 맞다고 생각합니다.

## 4. 생성형 AI와 협업한 방식

이번 프로젝트에서 생성형 AI는 단순히 모르는 문법을 질문하는 도구 이상이었습니다. 수집기 구조, 모델 구성, Python 코드와 분석 스크립트, 실험 설계와 해석에 상당 부분 관여했습니다.

직접 수행한 역할은 급등주 예측이라는 문제를 제안하고 목표를 조정하는 일, AI가 제시한 결과의 숫자와 논리가 타당한지 질문하고 재확인하는 일, 서버를 운영하면서 오류를 찾는 일, 그리고 어떤 방향을 계속 시도하거나 중단할지 결정하는 일이었습니다.

코드와 모델을 전부 독립적으로 설계·구현했다고 소개할 수는 없습니다. 그렇다고 결과를 무비판적으로 받아들인 것도 아닙니다. 특히 서로 다른 분석의 분모, 입력 피처, 모델 경로, 거래비용 조건이 맞지 않는 문제를 검토하면서 AI가 만든 코드와 설명도 검증 대상이라는 점을 배웠습니다.

이 기록은 그러한 협업 방식까지 포함한 개발 경험에 관한 것입니다.

## 5. 왜 프로젝트를 끝냈는가

수익성이 입증될 때까지 무기한 모델과 피처를 추가하는 것이 적절한지 고민했습니다. 데이터 수집과 분석 환경은 구축했지만, 여러 검증에서 비용 차감 후 수익률은 기대에 미치지 못했고, 안정적인 우위를 확인할 근거도 충분하지 않았습니다.

프로젝트가 처음 의도했던 범위를 훨씬 넘어선 점도 영향을 미쳤습니다. 학업과 다른 활동 사이에서 투입할 시간과 우선순위를 다시 생각했고, 새 실험을 시작하기보다는 기존 결과와 코드를 정리해 남기는 쪽을 선택했습니다.

중단했다고 해서 급등주 예측이 원천적으로 불가능하다는 뜻은 아닙니다. 다만 이번에 수집한 데이터와 검증한 조건만으로는 실제 거래에 사용할 만한 성과를 입증하지 못했습니다.

## 6. 남긴 결과와 앞으로의 공개 범위

보존한 결과물에는 수집·전처리·학습 코드, 모델 파일, 주간 데이터, 미래 가격 진단, 연구 결과, 운영 로그와 백업 기록이 포함됩니다. 대부분의 원본 데이터와 운영 자료는 비공개 Google Drive에 보관하고 있습니다.

GitHub에서는 구현 구조와 진행 과정, 검증 과정에서 확인한 한계를 공유하려고 합니다. 원본 시장 데이터, 인증정보, 계정·서버 설정은 공개하지 않으며, 코드도 보안과 재배포 권한을 확인한 범위에서만 공개할 예정입니다.

프로젝트의 결과를 한 문장으로 정리하면 다음과 같습니다.

> 실시간 데이터를 모으고 분석하는 시스템은 만들었지만, 실제 거래비용을 넘는 예측 전략은 입증하지 못했다. 그 과정에서 데이터의 정합성과 평가 기준을 확인하는 일이 모델 자체만큼 중요하다는 것을 배웠다.
